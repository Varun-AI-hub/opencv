\section{Introduction}

\texttt{VideoCapture::get(CAP\_PROP\_FRAME\_COUNT)} queries the video
container's header to return the total number of frames.  In many
real-world files this value is unreliable --- it can exceed, equal, or
even be less than the number of frames that can actually be decoded.
Issue \#29722 documents crashes and infinite loops that arise when user
code trusts this count for loop termination.

This document explains the container-format mathematics behind the
problem and proves that event-driven loop termination (via
\texttt{cap.read()}) is the only mathematically correct approach.

%-----------------------------------------------------------------------
\section{Video Container Architecture}

\subsection{Logical Structure}

A video container file is partitioned into:
\begin{enumerate}
  \item \textbf{Index / Header} --- metadata: duration, frame count,
        bitrate, codec parameters.  Readable without decoding.
  \item \textbf{Media Streams} --- interleaved audio and video packets.
  \item \textbf{Codec Data} --- compressed frame payloads.
\end{enumerate}

\subsection{Frame Count Stored in the Header}

For MP4/ISOBMFF containers, the relevant atoms are:
\begin{itemize}
  \item \texttt{moov} (Movie Box) $\supset$ \texttt{trak} (Track Box)
        $\supset$ \texttt{tkhd} (Track Header Box) which stores
        \texttt{duration} in \emph{movie time-scale} units.
  \item \texttt{stts} (Sample-to-Time box): maps each sample group to
        its duration, from which frame count is derived.
\end{itemize}

The header frame count is:
\[
  N_{\text{header}} = \bigl\lfloor D \times \text{fps} \bigr\rfloor
\]
where $D$ is the duration in seconds and fps is the nominal frame rate.

\begin{remark}
$N_{\text{header}}$ is written by the encoder at file creation time.
If the encoder crashes, the write is incomplete, or the file is
subsequently truncated, $N_{\text{header}}$ will be wrong.
\end{remark}

%-----------------------------------------------------------------------
\section{Frame Count Reliability Problems}

\subsection{Case 1: Truncated File}

Let a file be truncated after byte offset $B_t < B_{\text{total}}$.
The header (at offset 0) is intact and claims $N_{\text{header}}$
frames, but only $N_{\text{actual}} < N_{\text{header}}$ frames are
physically present:
\[
  N_{\text{actual}} = \max \bigl\{ k : \text{packets for frames } 0 \ldots k-1
                                      \text{ lie within } [0, B_t] \bigr\}
\]

\subsection{Case 2: Variable Frame Rate (VFR)}

In VFR streams each frame has a \emph{Presentation Timestamp} (PTS):
\[
  \text{PTS}_k \in \frac{1}{\text{time\_base}} \mathbb{Z},
  \qquad \text{time\_base} = \frac{p}{q}\;\text{seconds}
\]

Frame $k$ occupies the interval $[\text{PTS}_k, \text{PTS}_{k+1})$.
Frame durations $\Delta_k = \text{PTS}_{k+1} - \text{PTS}_k$ are
non-constant.  The nominal fps used to compute $N_{\text{header}}$ is
typically the \emph{average} or \emph{declared} fps, which may not
match any actual inter-frame gap.  Hence:
\[
  N_{\text{actual}} = \sum_{k=0}^{\infty} \mathbf{1}[\text{frame } k
                        \text{ decoded successfully}]
  \;\neq\; N_{\text{header}}
\]

Determining $N_{\text{actual}}$ requires decoding \emph{every frame},
which is an $O(N_{\text{actual}})$ operation with no shortcut.

\subsection{Case 3: Broken Encoder}

Some encoders write the wrong value in \texttt{stts} or leave the
\texttt{duration} field as 0 (updating it only on clean close).  In
such cases $N_{\text{header}} = 0$ while $N_{\text{actual}} > 0$, or
vice versa.

\subsection{Summary Inequality}

In general:
\[
  N_{\text{actual}} \leq N_{\text{header}}
  \quad \text{(but can violate this for VFR)}
\]

Only the following is mathematically guaranteed:
\[
  \text{cap.read()} = \text{true} \iff \exists \text{ a decodable frame at current position}
\]

\section{Presentation Timestamps: Formal Definition}

\begin{definition}[Time Base]
The \emph{time base} of a stream is a rational number
$\tau = p/q$ seconds (typically $\tau = 1/90000$ for MPEG streams).
All timestamps are integers in units of $\tau$.
\end{definition}

\begin{definition}[PTS and DTS]
Each frame packet carries:
\begin{itemize}
  \item $\text{PTS}_k$ (Presentation Timestamp): when to display frame $k$.
  \item $\text{DTS}_k$ (Decode Timestamp): when to feed frame $k$ to decoder.
\end{itemize}
For B-frame encodings, $\text{DTS}_k \leq \text{PTS}_k$ with strict
inequality for out-of-order B-frames.
\end{definition}

\begin{definition}[Stream Duration in Frames]
\[
  D_{\text{stream}} = \text{PTS}_{\text{last}} + \Delta_{\text{last}} - \text{PTS}_0
  \quad [\text{in time\_base units}]
\]
\[
  N_{\text{header}} = \biggl\lfloor D_{\text{stream}} \times \frac{\text{fps\_declared}}{\tau^{-1}} \biggr\rfloor
\]
\end{definition}

\section{Correct Loop Pattern}

\subsection{Buggy Pattern (Index-Based)}

\begin{lstlisting}
cap = cv2.VideoCapture("file.mp4")
n = int(cap.get(cv2.CAP_PROP_FRAME_COUNT))  # unreliable!
for i in range(n):
    ret, frame = cap.read()
    process(frame)  # crashes if ret=False and frame=None
\end{lstlisting}

\textbf{Failure mode:} if $N_{\text{actual}} < N_{\text{header}}$, the
loop runs past the last decodable frame.  \texttt{cap.read()} returns
\texttt{(False, None)} and \texttt{process(None)} raises an exception.

\subsection{Correct Pattern (Event-Driven)}

\begin{lstlisting}
cap = cv2.VideoCapture("file.mp4")
while True:
    ret, frame = cap.read()
    if not ret:
        break
    process(frame)  # guaranteed frame is valid here
\end{lstlisting}

\textbf{Mathematical guarantee:} \texttt{cap.read()} returns
\texttt{False} if and only if the stream is exhausted or a
non-recoverable decode error occurs.  The loop body executes exactly
$N_{\text{actual}}$ times.
